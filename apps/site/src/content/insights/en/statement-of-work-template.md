A statement of work becomes useful when the project stops going according to the first conversation. It should make the boundary visible and define how both sides will handle new information.

In one self-reported consulting project, a mid-project strategy change effectively replaced two modules and added a third. The agreement said only that changes would be “mutually discussed.” It did not define who submitted a change, how it was approved, or whether schedule and fees could change. The work nearly expanded by months without a new commercial decision.

The lesson is operational: write the decision process before the pressure arrives.

## Copy this statement of work structure

| Section | What to define | Acceptance question |
|---|---|---|
| Business objective | Decision or outcome the project supports | Can both sides explain why the work exists? |
| Deliverables | Named artifacts, formats, owners, versions | Is each item observable? |
| Out of scope | Explicit exclusions and adjacent work | Can a new request be classified quickly? |
| Milestones | Dates, dependencies, review windows | Is each checkpoint tied to evidence? |
| Acceptance | Tests, approver, response period | What counts as accepted or rejected? |
| Client inputs | Data, access, people, feedback | What happens if an input is late? |
| Change control | Request, impact review, written approval | Who can approve time or fee changes? |
| Commercial terms | Fees and payment triggers | Which event creates an invoice? |
| Pause and exit | Non-payment, blocked access, termination | How is completed work handled? |

## 1. State the objective before listing tasks

Write the business decision the work supports. “Run a growth project” is not an objective. “Choose one acquisition channel for a 30-day pilot and deliver the evidence required to approve or stop it” is testable.

Public US acquisition guidance for a [performance work statement](https://www.acquisition.gov/far/37.602) distinguishes the required result from prescribing how every task must be performed. Commercial projects are not federal contracts, but the principle is useful: define observable outcomes and standards before filling the document with activity.

## 2. Make deliverables and exclusions symmetrical

For every deliverable, record format, quantity, owner, draft rounds, due date, and acceptance method. Then list what is not included.

If the deliverable is a launch plan, specify whether copywriting, design, media buying, community operations, translation, implementation, and post-launch support are included. “Support as needed” is not a boundary.

Out-of-scope items are not hostile. They help the client compare the fee to a real package and request additions deliberately.

## 3. Define acceptance with observable criteria

Avoid “to the client's satisfaction” as the only standard. Use evidence: required sections present, named tests passed, document delivered in an agreed format, workshop held with named stakeholders, or implementation observed for a defined period.

For each milestone, state:

- who reviews;
- what evidence they receive;
- how many business days they have to respond;
- what constitutes rejection;
- how corrections are handled;
- whether silence has any contractual effect.

The last point requires legal review. Do not invent it in delivery operations.

## 4. Record client inputs and dependencies

A project can be late because the consultant missed work, because access arrived late, or because a decision-maker did not review. The SOW should separate those cases.

List data access, account permissions, stakeholder interviews, feedback windows, approvals, and technical dependencies. Define how the schedule is re-planned when a required input is missing. This is more constructive than arguing about blame after the deadline.

## 5. Use written change control

A change request should contain the requested change, reason, affected deliverables, schedule impact, fee impact, dependencies, and approval record. Work outside the original scope begins only after the authorized people approve the change in writing.

Do not treat every clarification as a paid change. Use the original deliverable and acceptance criteria to distinguish clarification, correction, and expansion.

## 6. Tie payment to real project events

There is no universal payment split. Iris has historically used milestone structures such as 30/40/30 in some projects; that is a self-reported operating example, not a standard.

Choose triggers that match real risk: signature, discovery completion, delivery of a defined milestone, acceptance, or a calendar date. State invoice timing, currency, taxes, expenses, payment method, and pause conditions. Late-fee clauses and enforceability vary by location and must be reviewed by qualified counsel.

The [consulting pricing strategy](/en/insights/consulting-pricing-strategy) explains how to price a defined decision and artifact before translating it into milestones.

## A short change-request template

```text
Change requested:
Reason and source:
Original SOW section affected:
Deliverable impact:
Schedule impact:
Fee or payment impact:
New client inputs or dependencies:
Approved by client:
Approved by provider:
Effective date:
```

Attach the approved request to the project record. A call can explore a change; the written record authorizes it.

## Final review checklist

Before signing, ask one person who did not draft the SOW to identify the objective, every deliverable, every exclusion, acceptance owner, required client inputs, change approvers, invoice triggers, and exit conditions. Any answer that depends on oral memory belongs in the document.

This template improves project clarity but cannot determine the correct legal terms for a jurisdiction. Use qualified counsel for the MSA, liability, IP, privacy, tax, employment, late-payment, dispute, and governing-law provisions.
