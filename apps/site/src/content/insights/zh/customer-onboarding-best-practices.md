客户 onboarding 不是产品导览，而是从意图到用户能认出“这对我有用”的最短、负责任路径。

用户注册后离开，可能是需求弱，也可能是信息不确定、缺少数据、下一步不清楚、操作不可逆、配置太长，或所谓激活只测了活动，没有测价值。不要先加更多 tooltip，先诊断。

## Onboarding 优化地图

| 阻力 | 更好的设计 | 观察证据 |
|---|---|---|
| 空白页面 | 示例数据或实用模板 | 开始与编辑率 |
| 不知道要多久 | 展示步骤与预计时间 | 每步放弃率 |
| 怕做错 | 预览、撤销、草稿、明确权限 | 错误与恢复率 |
| 选择太多 | 一个主任务，逐步展开选项 | 首次价值时间 |
| 路径太通用 | 按任务选择起点 | 分人群激活率 |
| 系统状态隐藏 | 显示状态、进度和下一步 | 重复点击、支持工单 |
| 信任不足 | 解释数据用途和控制方式 | 授权完成、删除请求 |

## 1. 设计界面前先定义第一次价值

“创建账号”通常不是激活。竞品分析产品可能在用户得到并保存一份有用对比时激活；协作产品可能在两个人完成一次共同任务时激活；报告产品可能在决策人查看当前报告时激活。

把假设写成：“具有任务 X 的用户，在完成可观察行为 Z 时获得价值 Y。”然后检查 Z 是否能预测继续使用或付费。

## 2. 减少不确定性，而不只是点击数

如果用户不知道数据会怎样、选择能否撤销，三步流程也可能比五步更难。

展示预计时间、所需输入、进度、隐私影响和下一结果；允许保存草稿与安全退出。错误提示要回答：发生了什么、工作是否保留、下一步怎么做。

## 3. 尽早让产品展示价值

在要求复杂配置前，使用示例数据、预览、模板、沙盒或一个范围窄的自动结果。只有当授权价值可见时，再要求更多权限。

示例和模拟数据必须明确标注，不能伪造成真实结果。

## 4. 每个阶段只有一个主任务

所有按钮都醒目，等于没有优先级。主操作要匹配用户当前任务，次要配置通过渐进披露出现。

无障碍也是清晰度的一部分：使用语义控件、可见焦点、易懂标签、足够对比度和明确错误。W3C 的 [WCAG 2.2 快速参考](https://www.w3.org/WAI/WCAG22/quickref/)提供正式成功标准与实现指引。

## 5. 把错误恢复设计进 onboarding

新用户一定会犯错。尽可能保留输入、允许撤销、提供已知可行的重启路径，并让真人支持可触达。一次成功恢复，有时比完美 happy path 更能教会用户。

同时记录错误与恢复，只知道错误次数并不完整。

## 6. 行为数据与访谈一起使用

漏斗告诉你用户停在哪里，不能可靠解释为什么。趁事件仍具体，访谈近期用户，让他复原尝试、期待、看到和随后做了什么。

[用户访谈证据卡](/zh/insights/customer-interview-template-startups)可以保留真实事件，而不是收集假设偏好。

## 最小测量方案

- 按来源与人群统计合格用户；
- onboarding 开始；
- 每个必经步骤；
- 错误与成功恢复；
- 首次价值时间；
- 分 cohort 激活率；
- 激活前支持联系；
- 激活后的留存或付费行为。

定义每个分子、分母、身份规则和时间窗。缺失事件是 unavailable，不是零。
