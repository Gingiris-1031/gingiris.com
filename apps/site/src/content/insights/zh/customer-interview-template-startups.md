早期用户访谈的目标不是收集“听起来不错”，而是减少一项产品决策的不确定性。2026 年 11 月 7–8 日的 workshop 中，我要求团队把友好聊天变成可复用的证据闭环：观察真实工作流、保留来源、每 5 场复盘一次，再决定是否改路线。

| 环节 | 时间 | 要了解什么 | 输出 |
|---|---:|---|---|
| 背景确认 | 5 分钟 | 角色、场景与触发点 | 人群备注 |
| 最近事件 | 10 分钟 | 实际发生了什么 | 行为时间线 |
| 屏幕共享 | 10 分钟 | 阻力与替代方案 | 观察记录 |
| 证据确认 | 5 分钟 | 承诺、反证与下一步 | 证据卡 |

## 用户访谈到底要解决什么问题？

一次访谈应服务于一个足够小的决策，例如：某一人群是否高频遇到问题、当前替代方案是否真的昂贵、激活在哪一步失败，或是否值得开展一个小试点。

访谈前先写清楚：“完成 5 场后，我们要决定是否为___用户做___。”这样可以避免谈话变成功能愿望池。

更强的信号通常来自真实行为：

- 用户能还原最近一次具体事件；
- 已经在使用某种替代方案；
- 已投入时间、金钱或内部协调成本；
- 同一阻力在工作流里反复出现；
- 愿意共享数据、介绍同事、参加试点或付费。

“听起来有用”不是承诺。“我周四可以介绍这个流程的负责人”更强，但在介绍真正发生前，也不能算已完成信号。

## 30 分钟用户访谈提纲怎么写？

### 1. 第一秒先说明边界

明确这次访谈是为了学习，不是销售。录音或记录前取得同意，说明材料用途以及是否匿名。未经许可，不要把私人对话直接变成公开营销案例。

可以这样开场：

> 我想了解你现在如何完成[具体任务]。这不是在测试你；相比礼貌反馈，我更希望知道哪里困难、哪里不相关。

### 2. 还原最近一次真实事件

围绕最近一次问题发生时提问：

1. 什么事情触发了这个任务？
2. 第一步做了什么？
3. 哪些人和工具参与？
4. 哪里开始变慢或失败？
5. 最后用了什么替代方案？
6. 结果造成了什么影响？

回答一旦变得抽象，就追问：“你可以带我走一遍最近一次吗？”真实过去行为通常比对假设功能的预测更可靠。

### 3. 直接观察现有工作流

如果是 Web 或 App 产品，让用户共享屏幕，并按平时方式完成相关任务。不要引导他去点击你希望他点击的按钮。观察停顿、忽略、跳出、打开的外部工具，以及用户自己使用的词。

当团队说“用户没看懂”时，真实原因可能是定位、引导、权限、缺少数据、信任，或产品根本没有解决这个任务。观察能帮助区分这些原因。

### 4. 主动问反证问题

不要只收集支持当前想法的证据。可以问：

- 什么情况下这个问题并不重要？
- 哪类人绝不会采用这套流程？
- 什么会让你继续使用现有替代方案？
- 不尝试这个产品的最强理由是什么？
- 我们哪项假设最可能是错的？

反证问题能避免团队把 5 场友好对话误读成市场确定性。

### 5. 用一个可观察动作结束

根据证据提出具体下一步：第二次工作流测试、小试点、导入一组数据、介绍团队成员或付费试用。不要施压；只有动作真实发生，才记录为承诺信号。

## 用户访谈证据卡怎么用？

每场访谈复制一张证据卡，并把观察与解释分开。

| 字段 | 记录内容 |
|---|---|
| 访谈编号与日期 | 稳定引用，不公开用户身份 |
| 人群与角色 | 只保留决策所需信息 |
| 触发点 | 什么事件启动了任务 |
| 现有流程 | 观察到的步骤、人员和工具 |
| 阻力 | 具体延迟、错误、成本或 workaround |
| 期望结果 | 用用户原话写“完成”的定义 |
| 现有替代 | 产品、表格、服务或人工流程 |
| 承诺信号 | 已实际提供的时间、数据、介绍、试点或付款 |
| 反证 | 哪些事实削弱当前假设 |
| 来源 | 经同意保存的录音、时间戳、截图或笔记 |
| 置信度 | 高/中/低及理由 |
| 影响决策 | 定位、激活、路线图、定价或人群 |

不要默认把敏感客户数据交给 AI。除非有合法且获批的处理理由，应先移除姓名、邮箱、商务条款、健康数据、账户标识和第三方信息。

## 如何判断是产品问题还是访谈误判？

发现失败后，先分类，再提功能。

| 失败类型 | 证据表现 | 下一项测试 |
|---|---|---|
| 定位 | 用户期待的是另一种结果 | 保持产品不变，测试更清晰承诺 |
| 激活 | 用户需要结果，但到不了首个价值点 | 不提供指导，观察完整 onboarding |
| 工作流适配 | 产品增加步骤或打断现有流程 | 测试集成或更窄任务 |
| 信任 | 用户不愿共享数据或依赖结果 | 测试证据、控制权与可解释性 |
| 优先级 | 问题真实但低频、低成本 | 换一个更高频人群验证 |
| 商业化 | 有价值，但买方、预算或套餐不清楚 | 访谈经济买方并测试试点 |

一场访谈可以发现问题，但不能证明问题有多普遍。分类的意义是决定下一步观察什么。

## 为什么每 5 场要复盘一次？

每 5 场复盘是一种实用节奏，不是统计学定律。把证据卡并排检查：

1. 同一人群里哪些行为重复出现？
2. 哪些口头表述被真实行为推翻？
3. 哪种阻力高频且代价明确？
4. 哪些用户给出了可观察承诺？
5. 哪些证据来自不同人群，不应混合？
6. 下一批什么结果会推翻当前主假设？

复盘最后只能进入四种决策之一：继续同一问题、收窄人群、做产品实验或停止假设。不要把每条评论直接变成 roadmap。

## 什么信号足够进入试点？

当问题、人群和下一步已经具体到可以验证时，才值得做试点。不要依赖固定访谈数量，而要同时看重复行为和真实承诺。

| 信号 | 弱版本 | 更强版本 |
|---|---|---|
| 问题 | “这很麻烦” | 反复延迟并有明确后果 |
| 替代方案 | “我们用表格” | 共享屏幕展示每周维护的 workaround |
| 紧迫性 | “下季度可能看看” | 已确认负责人和决策日期 |
| 访问 | “我可以问问团队” | 已完成介绍或数据授权 |
| 付款 | “应该愿意付费” | 已付费 discovery、定金或获批预算 |

本文的 workshop 案例属于第一方教学材料，不代表做固定数量访谈就能得到某个转化率。真正重要的是人群匹配、证据质量和团队如何反馈到产品。
