合同签了，不代表项目已经可以开工。客户 onboarding 的作用，是把商业承诺变成一套可运行系统：正确的人、输入、权限、里程碑和决策规则，在交付加速前全部到位。

Iris 的顾问项目经验里，很多被描述成“获客问题”的项目，真正瓶颈可能是激活、定位、测量或决策权。没有诊断就直接给建议，往往制造返工。

## 顾问项目客户入场清单

| 模块 | 开工前确认 | 负责人 |
|---|---|---|
| 决定 | 项目支持什么业务决定？ | 项目赞助人 |
| 范围 | 交付、排除项、版本、日期 | 双方项目负责人 |
| 人员 | 决策人、执行人、审批人、专家 | 客户负责人 |
| 输入 | 数据、文档、权限、访谈 | 指定提供人 |
| 基线 | 当前指标与定义 | 数据负责人 |
| 节奏 | 会议、异步更新、响应时限 | 双方 |
| 验收 | 证据、审核人、修改流程 | 审批人 |
| 变更 | 新需求如何影响时间与费用 | 授权负责人 |
| 商务 | 开票、报销、暂停条件 | 财务联系人 |
| 首个里程碑 | 第一周能观察到什么？ | 交付负责人 |

## 1. 重新说一遍业务决定

请项目赞助人补完一句话：“这次合作结束时，我们要拿到足够证据，决定是否 ___。”

这比“提升增长”更可验收。它可以是选择发布市场、判断 onboarding 是否为瓶颈、批准一个渠道试点，或定义一套可重复的顾问产品。

如果答案与报价单不同，先解决再 kickoff。

## 2. 把 SOW 变成运行地图

逐项核对交付、排除项、依赖、节点、验收与付款触发点。[SOW 工作说明书模板](/zh/insights/statement-of-work-template)负责定义文件结构，onboarding 则要给每一项分配人和日期。

```text
目标：
交付物：
明确排除项：
决策人 / 执行人 / 验收人：
所需权限和数据：
每周协作节奏：
第一个里程碑与日期：
验收证据：
变更批准人：
升级路径：
```

## 3. 写清决策权，而不只是参会人

十二个人参加 kickoff，也可能没人负责。明确谁提供数据、谁执行日常工作、谁批准变更、谁验收、谁解决阻塞。

不要默认最资深的人承担所有角色，把姓名写进项目记录。

## 4. 核验权限与基线定义

“我们有数据”不够。要确认属性、时间范围、事件定义、身份规则、来源归因与已知缺口。缺失数据标记为 unavailable，不能写成零。

定性证据也要列清：客户、销售电话、支持工单、产品录屏、历史实验和已有决定，并保留来源日期和定义。

## 5. 约定沟通与响应窗口

定义决定存在哪里、文件存在哪里、什么渠道用于紧急事项、双方通常多久响应、输入延迟后如何处理。聊天群不是天然的项目记录，关键决定需要总结并落档。

## 6. 第一周必须产出证据

第一个里程碑应该尽早暴露“问题找对了吗”。它可以是一份漏斗基线、五张用户证据卡、竞品决策图或发布准备度审计。

不要第一周就打磨最终大报告，先产出能低成本改变计划的东西。

## 应暂停入场的信号

- 没有决策人可以参与；
- 每次会议目标都变化；
- 权限无法提供，也没有替代证据；
- 客户期待明确排除在范围外的工作；
- 成功依赖一个没人能定义的指标；
- 开票或采购负责人不清楚；
- 可识别客户证据没有使用授权。

在这里暂停，是保护双方，比项目中段才发现便宜得多。

最后让客户负责人用自己的话复述目标、下一节点、负责人、会议节奏、验收和变更流程。项目不再依赖某个人的记忆，才算 onboarding 完成。需要把模糊需求整理成有边界的合作，可以查看 [Gingiris 顾问服务](/zh/services)。
