# 开源产品发布第一周该做什么

*出海实战手册 · 第 17 篇 | 从 0 到 6000 Star 的发布闭环设计*

---

2022 年 8 月 3 日凌晨 1 点 47 分，我坐在研发小哥旁边盯着他改字号。

官网是开源前一天才搓出来的。我说你把这个再放大点，他改完我刷新一遍，又说不对再调回去。整个团队疯狂加班了一个星期——因为我们 7 月 24 号才决定要开源。一个星期。从拍板到上线，所有准备时间只有一个星期。

那天凌晨点下 Public 按钮的时候，我心里没底。我们之前从来没做过开源，对开源一无所知。

然后第一天来了 200 个 GitHub Star。第二天 800 个。第三天又涨了 1000 个。第一周结束——6000 Star。

后来做顾问，从去年到今年又辅导了好几个项目做开源发布。我把当时的经验总结成了一套 SOP，在不同项目上反复验证。发现一件事：发布第一周做对了什么、做错了什么，基本上决定了这个项目后面半年的走势。

---

## 发布前最重要的事不是写代码，是讲对故事

很多团队觉得开源发布就是把仓库设成 Public，写个 Readme，发条推。

不是。

开源发布的第一步是——**让用户在 10 秒之内知道你是谁。**

我准备 AFFiNE 发布的时候，先去研究了当时开源界一个很知名的项目叫 AppFlowy。它比我们早开源，已经有 3 万 Star。我把 AppFlowy 放在谷歌里搜索，把时间调回到它开源的那一个星期——看它发了哪些站点、准备了哪些内容、Readme 怎么写、社群怎么运营。

我总结下来，AppFlowy 做对了几件关键的事。第一，Readme 图文并茂，小白也能看懂，没有上手门槛。第二，它准备了一篇蹭 Notion 的文章——它是第一个声称自己是「开源的 Notion 替代」的项目。这篇文章流量很大，后来被三四十个站点转载或翻译。第三，它的社群公告写得清楚，和用户之间的沟通方式是真诚且有结构的。

（我还去 AppFlowy 的社群里潜水了。做调研这件事，我是认真的。）

它蹭了 Notion，我们就去蹭 Notion 和 Miro。它在哪些导航站发，我们就去哪些导航站发。它的 Readme 图文并茂，我们也做图文并茂的 Readme。

但这里有一个很多人忽略的点：**蹭对标不丢人。** Notion 也是和 Evernote 对比起来的。很多团队不乐意说「我是谁的 alternative」，觉得像 copycat。但现在产品太多了，你怎么让用户一开始就把这个锚点给你锚住？你得让他在 10 秒钟之内快速 get 你的价值主张。你和一个知名竞品比，打穿一个痛点，远比同时打五个痒点效果好得多。

我后来辅导的所有开源项目，主动打「我是谁的开源替代」出来的效果，基本都比一堆形容词堆砌好很多。

---

## 第一周的节奏：24 小时之内必须做完的事

AFFiNE 开源当天，我做了这些事：准备了图文并茂的 Readme，发了蹭 Notion 和 Miro 的核心文章，提交了所有能提交的开源导航站——AppFlowy 出现过的那些站点我全部扒了下来，免费的导航站能直接提交的我都提交了一遍。

然后是私信。我去私信了 Notion 和 Miro 在 Twitter 上的粉丝，大概私信了几百个——不是一天私信那么多，是连着一周持续在发。

最关键的渠道是 Reddit。我在 Reddit 上发了 10 个帖子，4 个帖子火了，带来大概 20 万曝光，至少转化了 2000 个 Star。（当时 Reddit 规则还没有现在这么严格，现在再这么干难度大很多。）

把这些动作拆开看，核心就四件事：

**第一，价值主张。** 一句话说清楚你是什么。我们说的是「Notion + Miro 的开源替代」——不完美，但够清楚。

**第二，一篇可以被二次传播的核心文章。** 这篇文章是所有后续流量的蓝本。其他自媒体转载、翻译、引用，都是从这篇文章开始的。AppFlowy 当时那篇文章被三四十个站点提到，这就是「一篇内容撬动整个传播链」的逻辑。

**第三，渠道地毯式覆盖。** Reddit、Twitter、Medium、Hacker News、V2EX、各种开源导航站——24 小时之内尽可能多地铺出去。不是撒网碰运气，是事先调研好竞品出现过的所有渠道，然后全部覆盖一遍。

**第四，私信精准触达。** 竞品的粉丝就是你的潜在用户。私信 Notion 和 Miro 的 follower，告诉他们有一个开源替代出现了——转化率不高，但架不住基数大。

这四件事，在 24 小时之内全部打出去。不是慢慢来，是集中火力引爆。

## 为什么第一周这么关键：早期关注形成的飞轮

GitHub 有一个叫 Trending 的榜单——日榜、周榜、月榜。上了 Trending 意味着可能被更多开发者看到。但 GitHub 没有公开一个可以稳定复现的单一公式；我在当时项目里的观察是，短期关注速度与上榜机会有关，不能把它写成官方算法或结果保证。

这就是为什么第一周的节奏要快。你需要在 72 小时内制造足够的增速，上 GitHub Trending 日榜。上了日榜之后，Trending 本身会给你带来新的流量，新的流量又推高增速——飞轮就转起来了。

AFFiNE 从 2022 年 8 月到 12 月，上了 28 次 GitHub Trending。43 天突破 10000 Star。到今天累计超过 6 万 Star，覆盖 100 多个国家和地区。

但这个飞轮的起点，就是第一周那 6000 Star 带来的初始增速。

我为什么能有底气说这些？不是因为 AFFiNE 一个案例。是因为后来做顾问，同样的方法论教给不同团队，反复验证——只要你把价值主张、核心内容、渠道覆盖和精准触达这四件事在第一周做到位，它就是 work 的。

最近一个案例是 Insforge——发布后进入过 GitHub Trending，第三天打 Product Hunt 拿了日榜第一，后来也进入了 YC。这里是时间顺序，不足以证明某一次流量表现直接导致录取；它的发布 SOP 和我说的这套有很多相似之处。

## 大家都会犯的错：把发布当成一天的事

我辅导过的团队里，最常见的问题不是不努力，是把发布当成「一天的事」。

发布日热热闹闹，发了推、发了帖、私信了一波，然后——就没有然后了。

错。发布是一整周的事。甚至可以说，发布日只是第一天，后面六天才是真正拉开差距的地方。

第一天的 Star 来自你的主动推广。第二天到第七天的 Star 来自飞轮效应——但飞轮不会自己转，你得持续加力。

具体来说，发布后一周每天要做的事：每天在 3-5 个新的 Reddit 子版块发帖或互动。每天在 50-100 个海外开发者群组里分发内容。持续私信、持续回复评论、持续和每一个给你反馈的用户沟通。每天早晚各记录一次 Star 数量，形成数据曲线，分析增长来源。

如果某一天 Star 增速掉了——立即复盘，补充渠道。流量不会自己来，尤其是前一周。

而且，发布后的社区回复速度极其关键。你在 GitHub Issues 里三小时内回复和三天后回复，带来的用户感知完全不同。我当时做 AFFiNE 的时候，有一个孟加拉的用户为了成为我们的实习生，把我们某个测试版本的 bug 找了 20 多个，做成一份 PPT 发给我。还有一个台湾的用户沉寂了半年，突然给我写了一封 2000 字图文并茂的长评——她说「如果不是因为你太真诚我不会花两小时写这个」。

这些用户后来成了我们最坚定的种子用户。一个好的用户可以给你带 1 万个注册甚至付费用户。但你得先让他感受到你是认真的。

## 最贵的坑：发布了，但没想清楚接下来干什么

我见过太多团队，发布做得漂漂亮亮，Star 涨上去了，然后——不知道怎么把 Star 变成用户，把用户变成收入。

开源发布之后，你会收到大量集成咨询、合作请求、用户反馈。这个时候最大的坑是：被第一波用户的热情牵着走，什么都答应，什么都想做。

我们当时的教训是——1 万 Star 之后当即立断开始了最大规模的重构，一行代码不留。因为开源之前的代码架构撑不住后面的产品需求。但这个重构以用户体验为代价，等于你刚获了一大波关注，然后产品体验反而变差了。

反过来说，如果发布之前就想清楚了商业化路径——开源是为了影响力、招聘、商业化还是融资？API 和 Self-host 版本怎么定价？开发者社区和 ToB 客户怎么分别服务？——你才能在发布后有序地承接住这波流量，而不是被流量冲着跑。

准备好商业模式再开源，才能承接住开源这个 action 带来的流量，避免浪费。开源的本质是请 developer 贡献影响力，请 ToB 客户贡献钱。这两件事在发布之前就要想清楚。

## 同样的方法论，为什么有人做到有人做不到

我的 PH 打榜文档帮助至少 30 个团队拿到了日榜第一。这个文档在我去字节之前就已经在所有大厂疯传了，被几百上千人看过。

但为什么只有 30 个团队能拿到日榜第一？

因为大家差的是执行。同样一套方法论，谁能精准地拿捏好每一个细节的边界——这才是真正考验功夫的地方。

开源发布也一样。我今天讲的这些——价值主张、核心文章、渠道覆盖、精准触达、第一周节奏——听起来都不复杂。但落到执行层面：你的 Readme 能不能让一个路人在 30 分钟内看懂？你的核心文章能不能被其他人自发转载？你有没有提前两周就把 KOL 都联系好、把 Reddit 账号养好、把内容矩阵准备好？发布当天你的团队每个人精确到小时的任务分配是什么？

这些细节，光看方法论是学不会的。
